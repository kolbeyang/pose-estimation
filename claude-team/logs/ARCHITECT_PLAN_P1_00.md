# ARCHITECT_PLAN_P1_00: Verify Spirit of the Project

## Goal Summary

The capstone report describes a system where the optimization's objective function operates **directly on heatmaps** produced by a 2D pose estimator (Stacked Hourglass). The report explicitly states: "Our method operates directly on the heatmaps through reprojection: given a candidate 3D skeleton, we project its joints onto the 2D image plane and evaluate how well those projected positions align with the observed heatmaps." We need to verify that the motionbert-pose pipeline actually uses the real Stacked Hourglass heatmaps in its optimization scoring, and identify any other violations of the project's academic spirit.

## Findings

### Issue 1: Scoring uses synthetic Gaussian heatmaps, NOT real Stacked Hourglass heatmaps (CRITICAL)

**Both** `motionbert-pose/scoring.py` and `mediapipe-pose/scoring.py` use an **analytical Gaussian** approximation for the heatmap score:

```python
def heatmap_score(projected_2d, target_2d, visibility, sigma):
    diff = projected_2d - target_2d
    sq_dist = (diff ** 2).sum(dim=-1)
    log_likelihood = -sq_dist / (2.0 * sigma ** 2)
    return (log_likelihood * visibility).sum()
```

This is mathematically equivalent to placing a synthetic Gaussian blob centered on the extracted 2D keypoint and evaluating the projected skeleton against it. It does **not** use the actual (16, 64, 64) heatmaps produced by Stacked Hourglass.

The report says (Section IV.D): "Heatmap reprojection score: project 3D skeleton to 2D, sample heatmap values at projected joint locations." This implies the scoring function should **sample from real heatmaps**, not from synthetic Gaussians centered on argmax keypoints.

**Why this matters:** The whole thesis of the paper is that heatmaps encode richer information than extracted keypoints -- spatial uncertainty, multi-modality, etc. If we just extract the keypoint and build a synthetic Gaussian around it, we are throwing away everything that makes heatmaps useful. The optimization is effectively just minimizing reprojection error to a point estimate, which is no different from what any standard method does.

**The real Stacked Hourglass heatmaps are already available.** `detect.py` returns `all_heatmaps` (a list of (16, 64, 64) arrays), and these are passed through the pipeline but never used in `optimize.py` or `scoring.py`.

### Issue 2: The mediapipe-pose pipeline has the same problem (NOTED)

The mediapipe-pose pipeline also uses synthetic Gaussians. However, MediaPipe does not naturally expose heatmaps (it returns landmarks directly), so the analytical Gaussian was a reasonable choice there. The Stacked Hourglass network, by contrast, **is a heatmap-based detector** and its primary output IS the heatmap. For the motionbert-pose pipeline, there is no excuse not to use the real heatmaps.

### Issue 3: The overlay video also uses synthetic heatmaps (MINOR)

`mediapipe-pose/overlay_video.py` renders synthetic Gaussians for the overlay (`_render_heatmap`). For the motionbert-pose overlay (Phase 3 of the spec), the spec explicitly says: "These heatmaps should NOT be generated by applying a normal distribution over a single prediction point. Stacked Hourglass, if I'm not mistaken does have heatmaps as intermediate outputs, and it is those heatmaps that should be applied to our video frames." This is a Phase 3 concern but confirms the intent.

### Issue 4: No other spirit violations found

Other aspects of the project appear consistent with the report outline:
- The rigid skeleton model with FK is correctly implemented
- Joint angles are the optimization variables (not raw coordinates)
- Bone lengths are shared across frames
- Temporal smoothness penalties are included
- The pipeline uses real video from CMU Panoptic
- Adam optimizer with coarse-to-fine sigma schedule is used
- Evaluation uses MPJPE, P-MPJPE, and velocity error

### Step-by-Step Instructions

#### Step 1: Add real heatmap scoring to `scoring.py`

Add a new function `real_heatmap_score()` with this signature:

```python
def real_heatmap_score(
    projected_2d: torch.Tensor,       # (J, 2) projected positions in original image pixels
    heatmaps: torch.Tensor,           # (16, 64, 64) Stacked Hourglass heatmaps (MPII joints)
    affine: torch.Tensor,             # (2, 3) affine transform: 256-crop -> original pixels
    mpii_to_h36m_indices: list[int],  # mapping from H36M joint index to MPII heatmap index
    visibility: torch.Tensor,         # (J,) visibility weights
) -> torch.Tensor:
```

The function must:

1. **Convert projected_2d from original image pixels to 64x64 heatmap coordinates.** This requires inverting the affine transform (original pixels -> 256-crop coords) then dividing by 4 (256 -> 64). The affine maps from 256-crop to original, so we need the inverse: `pos_256 = affine_inv @ pos_orig`, then `pos_64 = pos_256 / 4`.

2. **Sample the heatmap at the projected location using differentiable bilinear interpolation.** Use `torch.nn.functional.grid_sample` with the heatmap as a (1, 1, 64, 64) input. `grid_sample` expects coordinates in [-1, 1], so normalize: `grid_x = pos_64_x / 63 * 2 - 1`, `grid_y = pos_64_y / 63 * 2 - 1`.

3. **Only sample for the 16 MPII joints that have heatmaps.** H36M has 17 joints but MPII has 16. The Hip joint (H36M index 0) is a synthetic midpoint -- it has no dedicated heatmap. For Hip, fall back to the analytical Gaussian score (average of left hip and right hip heatmaps, or just use the old formula).

4. **Take log of the sampled value** (plus small epsilon for numerical stability) and weight by visibility, just like the existing analytical version. The score should be: `sum(visibility[j] * log(max(heatmap_value[j], eps)))`.

5. **Return a scalar score** compatible with `compute_total_score`.

**Critical detail on the MPII-to-H36M mapping:** The heatmaps are in MPII 16-joint order. From `skeleton.py`, the `mpii_to_h36m()` function shows the mapping. We need a reverse mapping: for each H36M joint, which MPII heatmap index to sample. Construct this as a constant list. H36M joints that don't map to a single MPII joint (Hip=midpoint, Spine=midpoint) should use the analytical fallback.

The MPII joint indices and their H36M equivalents (from the existing `mpii_to_h36m` in skeleton.py) are:
- MPII 0 (R Ankle) -> H36M 3
- MPII 1 (R Knee) -> H36M 2
- MPII 2 (R Hip) -> H36M 1
- MPII 3 (L Hip) -> H36M 4
- MPII 4 (L Knee) -> H36M 5
- MPII 5 (L Ankle) -> H36M 6
- MPII 6 (Pelvis) -> used in H36M 0 (midpoint) and H36M 7 (midpoint)
- MPII 7 (Thorax) -> H36M 8, also used in H36M 7 (midpoint)
- MPII 8 (Neck/Nose) -> H36M 9 or 10
- MPII 9 (Head) -> H36M 10
- MPII 10 (R Wrist) -> H36M 16
- MPII 11 (R Elbow) -> H36M 15
- MPII 12 (R Shoulder) -> H36M 14
- MPII 13 (L Shoulder) -> H36M 11
- MPII 14 (L Elbow) -> H36M 12
- MPII 15 (L Wrist) -> H36M 13

### Risks and Edge Cases

1. **Heatmap resolution mismatch:** The Stacked Hourglass heatmaps are (16, 64, 64) in the 256x256 crop space. The projected 2D positions are in original image pixels. The affine transform maps 256-crop -> original pixels. Inverting this to go original -> 64x64 is critical. Off-by-one errors here will cause the optimizer to diverge.

2. **Differentiability:** `torch.nn.functional.grid_sample` is differentiable, so gradients will flow through the heatmap sampling. The heatmaps themselves are fixed (not optimized), so they just need to be tensors, not requiring grad.

3. **MPII joints only have 16 heatmaps.** H36M has 17 joints. The Hip (index 0) and Spine (index 7) are synthetic midpoints with no direct MPII heatmap. For these 2 joints, use the existing analytical Gaussian fallback. This is acceptable because the paper's claim about using heatmaps applies to the joints that actually have heatmap outputs.

4. **Heatmap values may be very small or zero.** Taking log(0) = -inf. Use `log(max(value, 1e-8))` as a floor.

5. **Coarse-to-fine schedule:** The existing sigma schedule controls the analytical Gaussian width. With real heatmaps, we can either: (a) apply a Gaussian blur to the real heatmaps at each step (matching the coarse-to-fine philosophy), or (b) use the real heatmaps directly (they already have a natural spatial extent). **Recommendation:** Start with (b) for simplicity. The Stacked Hourglass heatmaps already have a spatial extent roughly equivalent to a modest sigma. If the optimizer struggles to converge, add option (a) as a follow-up.

6. **Performance:** `grid_sample` is very fast (single bilinear lookup per joint per frame). No performance concern.

7. **The heatmaps are per-frame but the affine is shared** (same bbox across all frames). This is already how `detect.py` works -- the bbox is the union across frames, so the affine is the same for all frames. Confirm this when implementing.

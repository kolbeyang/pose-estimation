6. **Implement new 3-category joint mapping** -- 12 direct eval joints, 2 synthesized (Pelvis, Base of Neck), mode-specific optimization-only joints. Remove all computed midpoints from the skeleton.

The phases below are ordered so that foundational structural changes land first (directory renames, skeleton rework) before dependent changes (heatmap fixes, tests, isolation). Each phase produces a testable intermediate state.

## Discussion

### Current Skeleton (16 joints)

The current skeleton in `skeleton.py` has 16 joints in a single hierarchy:

```
Hip(0) -> RHip(1) -> RKnee(2) -> RAnkle(3)
Hip(0) -> LHip(4) -> LKnee(5) -> LAnkle(6)
Hip(0) -> Spine(7) -> Thorax(8) -> Neck(9)
                                -> LShoulder(10) -> LElbow(11) -> LWrist(12)
                                -> RShoulder(13) -> RElbow(14) -> RWrist(15)
```

Problems with the current skeleton:
- **Joint 0 ("Hip") is a computed midpoint** in both MediaPipe (midpoint of LHip/RHip) and COCO19 GT (maps to BodyCenter which is close but not identical to midpoint of hips). Only MotionBert/MPII has it as a direct detection (MPII[6]).
- **Joint 7 ("Spine") is always a computed midpoint** -- `coco19_to_h36m` computes it as `(joints19[2] + joints19[0]) / 2.0`, `mediapipe_to_h36m` computes it as `(Hip + Thorax) / 2.0`. No detector provides this directly.
- **Joint 8 ("Thorax")** maps to MPII[7] (direct) for MotionBert, but for MediaPipe it is `midpoint(LShoulder, RShoulder)`. For COCO19 GT it maps to COCO[0] ("Neck" in Panoptic naming).
- **Joint 9 ("Neck")** maps to MPII[9] (Head) for MotionBert, MP[0] (Nose) for MediaPipe, COCO[1] (Nose) for GT. These are different anatomical points.

The SPEC mandates removing all inferred/computed midpoints from the optimizer's skeleton. The new skeleton must have:
- 12 direct eval joints (Category 1)
- 2 synthesized joints (Category 2): Pelvis and Base of Neck
- Mode-specific optimization-only joints (Category 3): Thorax + Head Top for MotionBert; Nose for MediaPipe

### New Skeleton Design

The new skeleton needs a **different joint set depending on the pipeline mode**. This is a significant architectural change. Two design options:

**Option A: Variable-size skeleton (MotionBert: 16 joints, MediaPipe: 15 joints)**
- Pros: Clean, no unused joints
- Cons: Every function taking `NUM_JOINTS` must be parameterized, FK chain differs, bone_lengths differ, config rotation_penalty_multipliers differ, all tests must handle both

**Option B: Fixed 16-joint skeleton with mode flag**
- Skeleton always has 16 joints but the joint meanings change slightly per mode
- Cons: Some joints are "placeholder" in one mode

**Recommended: Option A with a clean abstraction.** The skeleton module exports two concrete skeleton configs (MotionBert and MediaPipe), each defining its own joint list, parent hierarchy, rest directions, bone lengths, and eval joints. All downstream code references `skeleton_config.num_joints`, `skeleton_config.eval_joints`, etc. This is cleaner and matches the SPEC's "no inferred midpoints" principle.

However, given the scope of this change and the need to keep the FK chain working, the most pragmatic approach is:

**Recommended approach: Two skeleton definitions sharing common structure.**

Both skeletons share the same 12 eval joints and 2 synthesized joints (indices 0-13). They differ in the optimization-only joints:
- **MotionBert skeleton (16 joints):** 14 shared + Thorax(14) + HeadTop(15)
- **MediaPipe skeleton (15 joints):** 14 shared + Nose(14)

The FK chain parent hierarchy must be redesigned:

**New shared joint layout (indices 0-13):**
```
Pelvis(0) [root, synthesized: midpoint(RHip, LHip) for MediaPipe, direct for MotionBert/GT]
  -> RHip(1) -> RKnee(2) -> RAnkle(3)
  -> LHip(4) -> LKnee(5) -> LAnkle(6)
  -> BaseOfNeck(7) [synthesized: midpoint(LShoulder, RShoulder) for MediaPipe, direct for MotionBert/GT]
     -> RShoulder(8) -> RElbow(9) -> RWrist(10)
     -> LShoulder(11) -> LElbow(12) -> LWrist(13)
```

**MotionBert extra joints:**
```
  Pelvis(0) -> Thorax(14) [MPII[7], between Pelvis and BaseOfNeck]
  BaseOfNeck(7) -> HeadTop(15) [MPII[9]]
```

**MediaPipe extra joint:**
```
  BaseOfNeck(7) -> Nose(14) [MP[0]]
```

**CRITICAL ISSUE:** The FK chain requires a connected tree. In the old skeleton, the path from Pelvis to shoulders went through Spine -> Thorax -> Shoulder. In the new skeleton, `BaseOfNeck` is directly a child of `Pelvis`, and shoulders branch from `BaseOfNeck`. This means the FK chain from Pelvis to BaseOfNeck is a single long bone (no intermediate Spine/Thorax in the shared joints), which is less constrained.

For MotionBert mode, Thorax(14) sits between Pelvis(0) and BaseOfNeck(7) on the FK chain. The parent hierarchy should be:
```
Pelvis(0) -> Thorax(14) -> BaseOfNeck(7)
```
This means Thorax is an intermediate FK joint even though it's not evaluated.

For MediaPipe mode, there is no intermediate joint, so the FK chain is:
```
Pelvis(0) -> BaseOfNeck(7)
```
This is a single bone from pelvis to base of neck (~0.44m), which is coarser but acceptable since MediaPipe doesn't detect Thorax.

**Revised approach:** Given these complexities, the cleanest implementation is two separate skeleton definition objects (one per mode) that share the same eval joint semantics but have different FK hierarchies.

### Stretched Heatmap Bug

In `scoring.py:generate_synthetic_heatmaps()`, line 367: `sigma_hm = sigma / sx` where `sx = w / heatmap_size`. If the image is 1920x1080, `sx = 1920/64 = 30`, `sy = 1080/64 = 16.875`. But the code uses a single `sigma_hm` for both X and Y dimensions (line 382: `sq_dist = (xx - cx_hm) ** 2 + (yy - cy_hm) ** 2`). This creates a circular Gaussian in heatmap space, which when mapped back to pixel space becomes an ellipse stretched horizontally (because `sx > sy`).

The fix: use separate sigma values for X and Y, or normalize coordinates to produce circular Gaussians in pixel space. The simplest fix is: `sigma_hm_x = sigma / sx`, `sigma_hm_y = sigma / sy`, then `sq_dist = ((xx - cx_hm) / sigma_hm_x) ** 2 + ((yy - cy_hm) / sigma_hm_y) ** 2`, and `heatmaps[f, j] = np.exp(-sq_dist / 2)`.

Wait -- actually re-reading more carefully: the Gaussian is defined in heatmap coordinates as `exp(-((x-cx)^2 + (y-cy)^2) / (2 * sigma_hm^2))`. In pixel space, `px = x * sx`, `py = y * sy`, so the Gaussian in pixel space is `exp(-((px/sx - cx)^2 + (py/sy - cy)^2) / (2 * sigma_hm^2))`. Expanding: `exp(-(px - cx*sx)^2 / (2 * sigma_hm^2 * sx^2) - (py - cy*sy)^2 / (2 * sigma_hm^2 * sy^2))`. The pixel-space standard deviations are `sigma_hm * sx` (x-direction) and `sigma_hm * sy` (y-direction). Since `sigma_hm = sigma / sx`, the pixel-space sigmas are `sigma` (x) and `sigma * sy/sx` (y). For a 1920x1080 image, `sy/sx = 1080/1920 = 0.5625`, so the Y sigma is 56% of the X sigma -- the Gaussian is stretched horizontally (wider in X, narrower in Y). This matches the reported bug.

**Fix:** Use `sigma_hm_x = sigma / sx` and `sigma_hm_y = sigma / sy` separately: `sq_dist = ((xx - cx_hm)**2) / sigma_hm_x**2 + ((yy - cy_hm)**2) / sigma_hm_y**2`.

**Implementation:**

1. **Use separate sigma for X and Y dimensions:**

3. **Also update the affine-to-grid conversion in `heatmap_score_batch()`** if the scoring pathway assumes isotropic scaling. Check that `crop_to_hm_ratio` handles non-square images correctly.

Currently in `heatmap_score_batch()`, the crop_to_hm_ratio is 1.0 for synthetic heatmaps. The affine maps `[0, heatmap_size-1]` to `[0, image_width-1]` in X and `[0, image_height-1]` in Y. The `sx` and `sy` in the affine already encode the different scales. The grid_sample code uses:
```python
x_crop = (hm_proj[:, :, 0] - tx) / sx
y_crop = (hm_proj[:, :, 1] - ty) / sy
```
These are in heatmap-coordinate space (0 to 63). Then `hm_x = x_crop / crop_to_hm_ratio` (which is 1.0), then `grid_x = hm_x / (hm_w - 1) * 2 - 1`. This should correctly handle non-square images since sx and sy encode the appropriate scales. The issue is only in the Gaussian generation, not in the scoring.

# Plan: Fix MotionBert Optimizer Regression

## Problem Overview

The optimizer hurts MotionBert by -6.6% VW-SI-MPJPE (only 6/25 examples improved) while helping MediaPipe by +2.1%. The target is to make optimized MotionBert 2% better than raw.

## Investigation Findings

### Finding 1: The optimizer makes MotionBert JERKIER, not smoother

Contrary to the initial "over-smoothing" hypothesis, the data shows the opposite. On example `171204_pose3_2000` (worst regression at +55.8%):

- GT mean eval-joint speed: 0.13 cm/frame
- Detector mean speed: 0.16 cm/frame (close to GT)
- Optimized mean speed: 0.25 cm/frame (1.9x GT, 1.6x detector)

Individual joints are worse: LElbow goes from 0.98x GT (detector) to 3.14x GT (optimized). The optimizer is introducing oscillations into already-smooth MotionBert output.

This pattern is consistent across examples:
- `171204_pose1_1000`: Opt/Det speed ratio = 2.81x
- `171204_pose2_2000`: Opt/Det speed ratio = 2.35x
- Velocity errors (MPJVE) increase on 19/25 MotionBert examples

**Root cause**: The heatmap loss gradient pushes joints to new positions each frame independently, fighting the smoothing penalties. For MediaPipe (noisy input), this adds useful signal. For MotionBert (already smooth), it adds noise.

### Finding 2: MotionBert bone lengths are severely distorted

On `171204_pose3_2000`:
- RAnkle bone: 11.5 cm detector vs 39.3 cm GT (0.29x ratio)
- LAnkle bone: 11.7 cm vs 36.7 cm GT (0.32x ratio)
- Spine: 52.5 cm vs 27.1 cm GT (1.94x ratio)

The median bone lengths across frames will partially average this, but the FK model operates with fundamentally wrong proportions for MotionBert. When the optimizer adjusts rotations to match heatmaps, the wrong bone lengths amplify small angle changes into large position errors.

### Finding 3: Scale factors are within bounds

All optimal scale factors are between 0.85 and 1.11 -- well within the (0.5, 2.0) search bounds. The `minimize_scalar` bounded approach is not saturating.

### Finding 4: SI-MPJPE and VW-SI-MPJPE use different scale optimization functions

`si_mpjpe()` uses `optimal_scale()` (unweighted), while `vw_si_mpjpe()` uses `_optimal_scale_weighted()` (visibility-weighted). Both compute the scale that minimizes their respective metric. This is mathematically correct, but we should verify they are consistent.

### Finding 5: The rotation penalty multipliers are uniform-ish and low

Current config:
```
Pelvis: 3.0, Hips: 1.0, Knees: 0.5, Ankles: 0.2
Spine/Neck: 1.0, Head: 0.5
Shoulders: 0.5, Elbows: 0.3, Wrists: 0.1
rotation_penalty_scalar: 10.0
```

Multiplied by scalar=10.0, the actual weights range from 1.0 (wrists) to 30.0 (pelvis). For MotionBert's already-smooth output, these penalties are too weak relative to the heatmap gradient -- the heatmap loss overwhelms them.

## Experiment Plan (in priority order)

### Phase 1: Rotation Penalty Tuning for MotionBert

**Hypothesis**: The rotation penalty weights are too weak to prevent the heatmap gradient from distorting MotionBert's already-accurate poses. Increasing `rotation_penalty_scalar` will reduce the jerkiness the optimizer introduces.

2. For each, measure: (a) VW-SI-MPJPE change vs raw, (b) mean speed ratio (optimized/detector), (c) MPJVE change.
3. Find the value where VW-SI-MPJPE improves and speed ratio stays close to 1.0.

**Solution results**: (to be filled by Dev)

### Phase 2: Pipeline-Specific Optimization Configs

**Motivating observation**: MediaPipe input is noisy (high MPJVE ~3-7 cm/f), MotionBert input is smooth (low MPJVE ~0.2-3 cm/f). The same optimization hyperparameters cannot be optimal for both.

**Hypothesis**: MotionBert needs higher smoothing penalties and/or fewer optimization steps, while MediaPipe benefits from the current settings.

**Verification method**:
1. After Phase 1 identifies the right `rotation_penalty_scalar` for MotionBert, check if that same value hurts MediaPipe.
2. If yes, add pipeline-specific defaults: `motionbert_config.json` and `mediapipe_config.json` should have different `optimization` blocks with different `rotation_penalty_scalar` values.

**Solution**: If the sweep from Phase 1 finds a single value that works for both, just update the default. If not, the run config JSON files (`run_motionbert/run_full_config.json`, `run_mediapipe/run_full_config.json`) already contain their own `optimization` blocks -- just set different values in each.

### Phase 3: Verify SI-MPJPE Metric Consistency

**Motivating observation**: The spec notes that SI performance degrades after optimization, which shouldn't happen if scale=1.0 is in the search space.

**Hypothesis**: There could be a mismatch between how scale is computed during metric calculation. The `si_mpjpe` function computes its own scale, while `vw_si_mpjpe` computes a different (weighted) scale. If the optimizer improves raw MPJPE but the SI scale adjustment undoes that improvement, there's a problem.

**Verification method**:
1. Write a test in `experiment/test_si_consistency.py`:
   - Compute `si_mpjpe(pred, gt)` and get the scale factor `s`.
   - Manually compute `mpjpe(s * pred, gt)` and verify it equals `si_mpjpe`.
   - Compute `vw_si_mpjpe(pred, gt, weights)` and get its scale factor.
   - Scale pred by that factor, compute `vw_mpjpe(scaled_pred, gt, weights)`, verify equality.
   - For VW-SI-MPJPE: verify that using scale=1.0 gives a result >= the optimal (i.e., the optimizer actually finds a minimum, not a worse point).
2. Use real data from one MotionBert example.

**Solution**: If inconsistency found, refactor so the exact same function is reused. If the bounded optimization misses the true minimum, widen bounds or switch to unbounded.

### Phase 4: Reduce Optimization Steps for MotionBert

**Motivating observation**: With 50 steps (current default), the optimizer has enough iterations to push joints away from good initial positions. Fewer steps = less damage from heatmap gradient.

**Hypothesis**: Reducing `num_steps` for MotionBert (e.g., 20 or 30) may give enough time for bone length regularization without over-adjusting joint positions.

**Verification method**: Run the same 3-5 examples from Phase 1 with the best `rotation_penalty_scalar` from Phase 1, varying `num_steps` in [20, 30, 50, 100].

**Solution**: Set `num_steps` in the MotionBert run config.

### Phase 5: Full 25-Example Validation

**Verification method**: Once Phases 1-4 identify the best config, run the full 25-example MotionBert pipeline and compute the optimization benefit summary. Target: optimized MotionBert beats raw by >= 2% on average VW-SI-MPJPE, with majority of examples improving.

## Implementation Notes

- All experiments should reuse existing output data where possible (trajectories.json from prior runs) to avoid re-running detection.
- The sweep scripts should be simple: load trajectories, re-run only the optimizer + evaluate, print results.
- No structural code changes needed for Phases 1-4 -- only config value changes and test scripts.
- If Phase 1-4 don't achieve the 2% target, investigate: (a) learning rate for MotionBert, (b) position_penalty_weight, (c) whether the heatmap blur sigma should be higher for MotionBert (more blur = less peaky gradients = less per-frame distortion).

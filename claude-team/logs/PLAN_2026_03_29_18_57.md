# PLAN: Unified Pose Optimizer (`pose-optimizer/`)

## Overview

We are building a unified `pose-optimizer/` subdirectory that combines the MediaPipe and MotionBert pose estimation pipelines into a single codebase with a shared optimizer, shared evaluation, and shared output structure. The original `mediapipe-pose/` and `motionbert-pose/` directories remain untouched.

**Key architectural decisions:**

1. **Shared 16-joint skeleton** -- the lowest common denominator across both pipelines, with no extrapolated joints.
2. **Camera abstraction** -- a single `Camera` class handling `world_to_camera`, `camera_to_world`, `camera_to_image` (numpy) and `camera_to_image_torch` (differentiable).
3. **Optimizer as pure function** -- `optimize(heatmaps_2d, raw_3d, camera) -> improved_3d`.
4. **Config-driven entrypoints** -- `uv run mediapipe.py config.json` and `uv run motionbert.py config.json`.
5. **Unified evaluation** with 9 metrics: MPJPE, P-MPJPE, SI-MPJPE, VW-MPJPE, VW-SI-MPJPE, MPJVE, SI-MPJVE, VW-MPJVE, VW-SI-MPJVE.
6. **Visibility weighting (VW)** based on frame-boundary projection of GT 3D, not detector confidence.
7. **Bias toward MotionBert implementation** when there are discrepancies.

## Discussion

### 1. Skeleton Mapping: The 16-Joint Lowest Common Denominator

Both implementations already use a 16-joint H36M skeleton (Head removed). The joint lists are nearly identical but have a critical difference at **joint index 9**:

| Index | `mediapipe-pose/skeleton.py` | `motionbert-pose/skeleton.py` |
|-------|------------------------------|-------------------------------|
| 9     | **Nose**                     | **Neck**                      |

In `mediapipe-pose/skeleton.py:122`, joint 9 maps to MediaPipe landmark 0 (Nose). In `motionbert-pose/skeleton.py:145,146`, joint 9 maps to MPII joint 9 (Head), and 10 maps to MPII joint 9 (Head) -- both get the same source, then Head (original index 10) is stripped by `h36m_17_to_16()` at `skeleton.py:198-207`. The result is that after the Head removal, joint 9 in motionbert-pose comes from MPII "Head" (top of head), not "Nose".

Meanwhile, the COCO19 GT mapping is consistent between both: `coco19_to_h36m()` maps joint 9 to COCO19 index 1 (Nose) in `mediapipe-pose/skeleton.py:199` and COCO19 index 1 (also labeled Nose) in `motionbert-pose/skeleton.py:189`. However, the motionbert skeleton *names* this joint "Neck" rather than "Nose".

**Decision:** For the unified skeleton, use the MotionBert naming convention ("Neck" at index 9) since we bias toward MotionBert. The COCO19-to-H36M mapping sends Nose (COCO19 index 1) there, and the MPII-to-H36M mapping sends MPII Head there. The MediaPipe mapping will send MediaPipe landmark 0 (Nose) there. These are all reasonable approximations of the same upper-head/neck region. The important thing is that the GT mapping and the detector mapping are consistent within each pipeline.

**The 16 joints (same as both existing skeletons):**
```
0=Hip, 1=RHip, 2=RKnee, 3=RAnkle, 4=LHip, 5=LKnee, 6=LAnkle,
7=Spine, 8=Thorax, 9=Neck/Head, 10=LShoulder, 11=LElbow, 12=LWrist,
13=RShoulder, 14=RElbow, 15=RWrist
```

**Parent hierarchy (identical in both):**
```python
PARENTS = [-1, 0, 1, 2, 0, 4, 5, 0, 7, 8, 8, 10, 11, 8, 13, 14]
```

**Eval joints:** Follow motionbert-pose which excludes Hip(0), Spine(7), Thorax(8), Neck(9) because these are computed midpoints that differ between detector, GT, and FK. This gives 12 eval joints: `[1, 2, 3, 4, 5, 6, 10, 11, 12, 13, 14, 15]`. See `motionbert-pose/skeleton.py:30-33`.

### 2. Camera Abstraction

Both existing implementations have a `Camera` class with identical projection math. The MotionBert version (`motionbert-pose/camera.py`) is more complete with `from_panoptic_calibration()`, `to_dict()`, `from_dict()` class methods. The MediaPipe version (`mediapipe-pose/model/camera.py`) adds a `reprojection_error()` method and `from_focal_length()`.

**The unified Camera must support:**
- `world_to_camera(points_3d_world, R, t)` -- extrinsic transform (currently a free function in `panoptic.py:107-125` in both)
- `camera_to_world(points_3d_cam)` -- inverse extrinsic (new, for completeness)
- `camera_to_image(points_3d_cam)` -- intrinsic projection (currently `world_to_image()` which is misnamed -- it projects *camera-space* points, not world-space)
- `camera_to_image_torch(points_3d_cam)` -- differentiable version
- `image_to_ray(points_2d)` -- back-projection for depth estimation (inverse of camera_to_image)
- Store R, t extrinsics alongside K intrinsics
- `from_panoptic_calibration()` class method

The key insight is that the current `world_to_image()` in both Camera classes actually does `camera_to_image()` -- it assumes points are already in camera coordinates. The `world_to_camera()` transform using R,t is done separately in `panoptic.py`. The new Camera should unify these.

### 3. Optimizer as Pure Function

Both optimizers use the same core approach: FK parameterization -> Adam optimization -> FK reconstruction. The differences:

| Aspect | MediaPipe (`mediapipe-pose/optimize.py`) | MotionBert (`motionbert-pose/optimize.py`) |
|--------|------------------------------------------|--------------------------------------------|
| Heatmap source | Analytical Gaussian from 2D detections (`scoring.py:10-34`) | Real SH heatmap sampling via `grid_sample` (`scoring.py:40-96`) |
| Input 2D | `target_2d: list[np.ndarray]` (pixel coords) | `heatmaps: list[np.ndarray]` (64x64 heatmaps) + `affine` |
| Batching | Per-frame loop only | Has `run_optimization_batched()` with vectorized FK and scoring |
| LR groups | 2 groups (pose, bone_lengths) | 3 groups (root_pos at 1.5x, angles, bone_lengths) |
| Anchor penalty | None | Optional `INIT_ANCHOR_WEIGHT` (default 0.0) |
| Blur | Fixed `SIGMA` parameter | `HEATMAP_BLUR_SIGMA` + optional coarse-to-fine schedule |

**Decision:** The unified optimizer will accept *both* heatmap types. The interface:
```python
def optimize(
    heatmaps_2d,        # (N, K, H, W) real heatmaps OR None
    target_2d,          # (N, K, 2) 2D landmark pixels OR None
    raw_3d,             # (N, K, 3) initial 3D predictions in camera space
    camera,             # Camera object
    config,             # OptimizationConfig dataclass
) -> np.ndarray:        # (N, K, 3) improved 3D predictions
```

For MediaPipe: `target_2d` is provided, heatmaps are generated as analytical Gaussians.
For MotionBert: `heatmaps_2d` is the raw SH output.

Use the MotionBert batched optimizer as the base since it is more mature (vectorized FK, batch scoring, 3 LR groups). Reference: `motionbert-pose/optimize.py:315-510`.

### 8. Heatmap Differences

**MediaPipe** (`mediapipe-pose/scoring.py:10-34`): Analytical Gaussian log-likelihood. No actual heatmap image is created. The score is `-sq_dist / (2 * sigma^2)` weighted by visibility. This is mathematically equivalent to sampling a Gaussian blob but avoids materializing images.

**MotionBert** (`motionbert-pose/scoring.py:40-96`): Samples real (16, 64, 64) Stacked Hourglass heatmaps using `F.grid_sample`. Only 14 of 16 joints are scored (Hip and Spine have no dedicated MPII heatmap). Uses confidence-weighted log-likelihood: `log(value * conf + eps * (1 - conf))`.

For the unified optimizer, the MediaPipe path should generate synthetic Gaussian heatmaps at a configurable resolution (e.g., 64x64) and pass them through the same `grid_sample` scoring pipeline. This unifies the scoring code path. The `gaussian_sigma` config parameter controls the Gaussian width.

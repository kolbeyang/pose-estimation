Expected savings: ~15-30s per additional example (MotionBERT), ~2-3s per additional example (MediaPipe).

## Critical Decisions Requiring Review

### 1. solvePnPRansac vs SQPNP divergence

The spec asked for unified solvePnP to match MediaPipe. The implementation uses different solver variants:

- **MediaPipe** (`run_mediapipe/detect.py:131`): `cv2.solvePnP(..., flags=cv2.SOLVEPNP_SQPNP)`
- **MotionBERT** (`run_motionbert/detect.py:729`): `cv2.solvePnPRansac(..., reprojectionError=8.0)`

```python
# run_motionbert/detect.py:729-731
success, rvec, tvec, _inliers = cv2.solvePnPRansac(
    obj_pts, img_pts, K, dist_coeffs, reprojectionError=8.0,
)
```

SQPNP was tried first and failed badly (mean depth 1.66m vs GT 2.62m) because MotionBERT has noisier 3D predictions than MediaPipe. RANSAC resolved this. The conceptual approach is unified (solvePnP-based), but the specific solver differs. **This is justified but worth being aware of.**

### 2. MPJVE degradation on pose1: 2.70 -> 14.93 cm/f (+453%)

solvePnPRansac finds a slightly different rotation per frame (~18 deg mean from identity, ~6 deg std frame-to-frame), introducing jitter that the old identity-rotation heuristic did not have. The optimizer reduces this downstream, but raw detector velocity smoothness is significantly worse on some sequences.

**If velocity smoothness matters for downstream tasks**, consider temporal smoothing of the solvePnP rotation (exponential moving average on `rvec`). This is logged as an open TODO.

### 3. Backward-compatible optional params with `or` guard

`run_motionbert/detect.py:298` and `:520` use `if model is None or device is None:` to decide whether to reload models internally:

```python
# run_motionbert/detect.py:298
if model is None or device is None:
    from stacked_hourglass import hg8
    device = device or _get_device()
    ...
```

This means passing `model` without `device` (or vice versa) silently discards the provided argument and reloads everything. Should be `and` with a guard for the mixed case. In practice unreachable because `detect_poses` always passes both or neither, but it violates least-surprise for direct callers.

## Issues with the Original Spec

1. **"solvePnP" is not one-size-fits-all.** The spec assumed MediaPipe's `SOLVEPNP_SQPNP` would work directly for MotionBERT. It did not -- MotionBERT's noisier 3D predictions required RANSAC. The spec did anticipate iteration ("If there was a degradation in performance, please hypothesize, verify, and iterate") which saved this from being a blocker, but the initial assumption that the same solver variant would work was incorrect.

2. **No MPJVE acceptance criteria.** The spec defined VW-SI-MPJPE thresholds (+/-5%) but did not mention velocity error. The +453% MPJVE degradation on pose1 passed the spec's acceptance criteria but is a meaningful regression that a velocity-aware threshold would have caught.

3. **Benchmark scope was underspecified.** The spec said "Run a few examples" but didn't define which examples or how many frames. Dan chose 3 examples with 100-150 frames. The pose3 example had 61 cm VW-SI-MPJPE (a known hard case), which dominated the mean and obscured the pose1 regression.

4. **Phase 3 had no performance timing requirement.** The spec said "optimize a bit better" and implied timing savings but didn't require measuring them. Verification relied on model-loading log line counts rather than actual wall-clock comparisons.

## Issues with Subagents / TOM.md Recommendations

1. **Dev agent (Dan) made good implementation decisions** -- choosing RANSAC after SQPNP failed, preserving the heuristic as a fallback, using optional params for backward compatibility. No complaints on execution quality.

2. **QA agent (Eve) was thorough and independent.** Found the `or`/`and` guard issue, the missing type annotation, the `landmarker.close()` not in `try/finally`. Good catches.

3. **Recommendation: Require baseline numbers BEFORE implementation begins.** Dan's Phase 2 report combined benchmarking and implementation, making it hard to verify the baseline was truly captured before code changes. The plan had this as a separate sub-phase, but the report doesn't clearly separate the timeline. TOM.md should enforce "commit baseline results to a file before touching any implementation code."

4. **Recommendation: Define acceptance criteria per-example, not just mean.** The +3.8% mean hid a +18.3% regression on pose1. The plan mentioned "No example regresses by more than 20% on any metric" but the MPJVE column was ignored (not in acceptance criteria). TOM.md should require per-example and per-metric acceptance tables.

5. **Recommendation: For refactoring phases (Phase 1, Phase 3), skip the full plan document.** Both plans were 200+ lines for straightforward changes. A checklist of files + a "Definition of Done" section would suffice. Save detailed plans for phases with ambiguity or risk (like Phase 2).

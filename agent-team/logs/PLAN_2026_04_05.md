**Title**: Understand the full error landscape before changing anything.

### Implementation

Run a battery of diagnostic experiments on the single test example (171204_pose1_sample) to build an evidence base. All scripts go in `experiment/`.

#### 0A. Visibility weight audit
- Run `experiment/audit_vw_si_mpjpe.py` on both MotionBERT and MediaPipe trajectories.
- Add per-joint **visible frame counts** to results.json (the spec explicitly requests this).
- Verify: do the visibility weights correctly reflect whether joints are in frame? Check that `compute_visibility_weights()` uses GT positions (not predictions) to determine visibility -- it does, confirmed in code. This is correct.
- **Key question**: Are ankle/knee joints frequently OUT of frame, meaning their large errors are being downweighted? Or are they IN frame and contributing heavily?

#### 0B. Heatmap quality audit for knees
- Write `experiment/audit_heatmap_quality.py`: For each frame, extract the heatmap score at the GT knee location vs. the predicted knee location. If the heatmap has no peak near the knee at all, the optimizer has no gradient signal to correct it.
- Sample 5-10 frames and visualize the knee heatmap channels (MPII channels 1=RKnee, 4=LKnee) overlaid on the frame. Are there peaks? Are they in the right place?
- This directly addresses Observation 2 from the spec: "Are there good heatmaps for the knees?"

#### 0C. Bone length analysis for MotionBERT knees
- The spec notes: "det R Knee bone: 0.99m vs GT: 0.44m". This means MotionBERT's raw 3D has knees WAY too far from hips.
- Investigate: Is this a problem with MotionBERT's normalized output, or with the `motionbert_to_camera_space()` scaling? The `_RELIABLE_BONES_FOR_SCALE` set is `{10, 11, 12, 13, 14, 15}` (arms only). Legs are excluded. If MotionBERT has bad leg proportions, the arm-based scale will make legs even worse.
- Print per-bone scale ratios for all 15 bones to see if legs are systematically different.

#### 0D. MediaPipe degradation root cause
- The optimizer makes MediaPipe WORSE. Possible causes:
  1. The optimizer is moving joints AWAY from their correct positions to maximize heatmap scores (heatmaps are noisy/wrong for some joints)
  2. The position/rotation penalties are constraining the skeleton in ways that increase error
  3. The FK parameterization + bone length sharing introduces error (roundtrip error in FK init)
  4. The learning rate or number of steps is wrong (10 steps may be too few to converge, or too many and it overshoots)
- Run: compare per-joint error BEFORE and AFTER optimization for MediaPipe. Which joints get worse?
- Run: check FK roundtrip error for MediaPipe vs MotionBERT init. If MediaPipe starts with a better skeleton, the FK roundtrip error might be introducing noise.

#### 0E. Run `audit_scale_effect.py` on both pipelines
- The scale factor bounds are [0.5, 2.0]. If scale is hitting bounds, the SI metric is not actually scale-independent.
- Check if the scale factor is pathological.

- Verify audit script outputs match stored results.json values.

## Phase 2: Fix MotionBERT Knee Scale Issue

**Title**: Improve MotionBERT bone length estimation to handle bad leg proportions.

### Implementation

The root cause hypothesis: MotionBERT's normalized output has systematically incorrect leg proportions (knees too far from hips). The current `motionbert_to_camera_space()` uses only arm bones (`_RELIABLE_BONES_FOR_SCALE = {10, 11, 12, 13, 14, 15}`) to compute the scale factor. This is correct behavior IF MotionBERT's legs are actually wrong in normalized space -- scaling them would not help, since the relative proportions are wrong.

However, the optimizer CAN fix this because it has:
1. Shared bone lengths (median across frames) -- these will be wrong for knees initially
2. Bone length learning (`bone_length_lr = 0.0001`) -- very slow, may not converge in 10 steps
3. Heatmap signal -- if knees have heatmap peaks, the optimizer can pull knees to the right place

**Changes needed (based on diagnostic findings)**:

#### 2A. Increase bone_length_lr for faster bone length convergence
- Current: `bone_length_lr = 0.0001`. With 10 steps, bones barely move.
- Test: Increase to 0.001 or 0.005 and see if knee bone lengths converge toward GT.

#### 2B. Initialize bone lengths from DEFAULT_BONE_LENGTHS instead of median of (bad) detections
- Current: `median_bone_lengths = np.median(np.array(all_bone_lengths), axis=0)`. If MotionBERT's knees are consistently wrong, the median will be wrong.
- Solution: Use a weighted blend of detected and default bone lengths, or clamp detected bone lengths to within a reasonable range of defaults.
- Alternatively: For joints where detected bone length differs by >50% from default, use default instead.

#### 2C. Consider per-joint bone length initialization
- For MotionBERT: if leg bones are systematically 2x too long, initialize those specific bones from defaults.
- This requires knowing which detector is in use. Could add a `pipeline_name` parameter to `optimize()` or just use a general "clamp to reasonable range" approach.

### Testing
- Run single MotionBERT example with modified bone length init.
- Check: Do knee bone lengths converge toward GT values (~0.42m)?
- Check: Does VW-SI-MPJPE decrease for knees specifically?
- Check: Does overall VW-SI-MPJPE improve?

### Definition of Done
- MotionBERT knee per-joint error reduced by >30% from current baseline.
- Overall MotionBERT VW-SI-MPJPE improved from 18.86 cm.

## Phase 3: Fix MediaPipe Optimization Regression

**Title**: Prevent optimizer from degrading MediaPipe results.

### Implementation

MediaPipe raw is already quite good (15.66 cm). The optimizer makes it worse. This is the hardest problem because the optimizer needs to help without hurting.

**Root cause investigation from Phase 0 will determine the approach. Likely candidates:**

#### 3A. Conservative optimization for good starting points
- If MediaPipe starts close to the truth, the optimizer may be adding noise via:
  - FK roundtrip error during initialization (positions -> FK params -> FK -> positions may not roundtrip perfectly)
  - Heatmap peaks not perfectly aligned with true joint positions (SH heatmap resolution is 64x64, there's quantization)
  - Position/rotation penalties fighting the heatmap score
- Solution: Add an **initial-pose anchor penalty** -- penalize deviation from the initial FK parameters. This prevents the optimizer from wandering too far from a good starting point.
- Implementation: In `compute_total_score_batch()`, add optional `init_positions` tensor. Compute `anchor_loss = ||positions - init_positions||^2`. Weight it with a config parameter `anchor_weight`.
- For MediaPipe (good starting positions), use higher anchor weight. For MotionBERT (bad legs), use lower anchor weight.
- OR: make anchor weight per-joint, so joints with high initial confidence keep their positions.

#### 3B. Visibility-weighted heatmap scoring
- Currently, the heatmap scoring uses `visibility_batch` (from SH detector) as confidence weights. But these may be noisy.
- If a joint has low SH visibility but the detector (MediaPipe) placed it correctly, the optimizer might move it to match a noisy heatmap peak.
- Solution: Increase `confidence_epsilon` so low-visibility joints are scored more conservatively.

#### 3C. Reduce optimization aggressiveness
- Fewer steps (already at 10) or lower learning rate.
- But this would also reduce MotionBERT improvement, so per-pipeline config may be needed.

#### 3D. Separate optimization configs per pipeline
- Add `motionbert_optimization` and `mediapipe_optimization` to `RunConfig`.
- MediaPipe gets: higher anchor weight, lower LR, fewer steps.
- MotionBERT gets: higher bone_length_lr, more steps, lower anchor weight.

### Testing
- Run single MediaPipe example with anchor penalty.
- Check: Does VW-SI-MPJPE improve (or at least not get worse)?
- Check: Does adding anchor penalty not hurt MotionBERT?

### Definition of Done
- MediaPipe optimized VW-SI-MPJPE is better than raw by at least 2%.
- MotionBERT is not degraded by the changes.

## Appendix: Hypotheses to Test

1. **H1: MotionBERT knee error is from bad normalized proportions, not scaling bug.** Verify by checking raw MotionBERT bone lengths in normalized space vs. expected proportions.

2. **H2: Knee heatmaps have weak or absent peaks.** Verify by inspecting MPII channels 1 (RKnee) and 4 (LKnee) in the SH output.

3. **H3: Visibility weights are binary and correct.** Verify by projecting GT to 2D and checking frame bounds. Already confirmed in code review -- `compute_visibility_weights` projects GT, not predictions.

4. **H4: FK roundtrip error is negligible.** Verify by checking the roundtrip error logged during optimization. If >1cm, the FK parameterization itself introduces error.

5. **H5: MediaPipe degradation is from heatmap-driven joint drift.** Verify by comparing per-joint error change from raw to optimized. If specific joints get worse, check if those joints' heatmap peaks are misaligned.

6. **H6: 10 optimization steps is insufficient for MotionBERT bone length convergence.** Verify by running with more steps and checking if bone lengths approach GT.

7. **H7: The heatmap_blur_sigma is wrong.** Current: 32.0 in motionbert-single.json but default is 4.0 in config.py. Higher blur makes the optimization basin wider but less precise. Need to find the right value for each pipeline.

8. **H8: `confidence_epsilon` is too small, causing low-visibility joints to be ignored.** Current: 1e-4. If a joint has 0 SH visibility, its heatmap contribution is `1e-4 * heatmap_value` which is nearly zero. This means the optimizer ignores low-confidence joints entirely, which may be correct OR may prevent fixing joints that the SH detector missed but are actually in frame.

## Appendix: Risk Assessment

- **Highest risk**: MediaPipe improvement. It's already good, and the optimizer is actively hurting it. Phase 3 (anchor penalty) is the critical intervention.
- **Medium risk**: MotionBERT knees. The underlying MotionBERT predictions may just be bad for legs. If heatmaps have no knee signal, no amount of optimization can fix this.
- **Lowest risk**: Hyperparameter tuning. This is mechanical but time-consuming.
- **Time estimate**: Phase 0 (1hr), Phase 1 (15min), Phase 2 (1hr), Phase 3 (2hr), Phase 4 (2-3hr compute), Phase 5 (1hr compute + validation).
